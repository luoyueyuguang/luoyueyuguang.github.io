## TF32：NVIDIA TensorFloat-32

聊浮点精度，`fp16` / `bf16` / `fp8` 天天见，但 **TF32（TensorFloat-32）** 很少被单独提起——因为它压根不是一种能"存储"的格式。它是 NVIDIA 在 **Ampere 架构的第三代张量核心**上加入的**计算模式**：用 fp32 的指数范围 + fp16 的尾数精度拼成一块 19-bit 的"虚拟格式"，专门用来加速 fp32 的矩阵乘和卷积。理解它，等于理解了"混合精度"这条路的起点。

一句话给直觉：

> TF32 取 fp32 的 8 位指数（偏置 127，**范围不变**）和 fp16 的 10 位尾数（含隐式前导位共 11 位有效），拼成一块 **19 bit** 的操作数。它在张量核心乘法前把 fp32 操作数临时截短到 10 位尾数，乘出约 21–22 bit 的乘积，再累加进**完整的 fp32**。它不是存储格式——内存里永远是 fp32，只有乘加的那一瞬间在张量核心内部被"瘦身"。代价是一点点精度，换来相对 fp32 CUDA 核心约 **8 倍**的矩阵乘吞吐。

### 位布局

TF32 是一种 **1 + 8 + 10 = 19 bit** 的三段式格式，但存放时占满 **32 bit**（与 fp32 同宽），未用的 13 bit 被填零：

```text
 1 bit   8 bits          10 bits
+------+---------------+--------------+
|  S   |   Exponent    |   Mantissa   |
|  1   |      8        |      10      |
+------+---------------+--------------+
   ←——————— 19 bit（塞进 32 bit 槽位）——————→
```

| 字段 | 位数 |
| --- | --- |
| sign | 1 |
| exponent | 8（偏置 127，同 fp32） |
| fraction | 10 |
| 总计 | 19（存放占 32 bit） |

普通数的表示与 fp32 同构，只是尾数变窄：

$$
x = (-1)^s \cdot 2^{E - 127} \cdot (1.f)_2
$$

$f$ 是 10 位小数。偏置 $127 = 2^{8-1} - 1$，与 [[learning/precision/fp32|fp32]] / [[learning/precision/bf16|bf16]] 完全相同。非正规数（subnormal）则取

$$
x = (-1)^s \cdot 2^{-126} \cdot (0.f)_2
$$

指数位和 fp32 一模一样，所以**动态范围与 fp32 完全一致**——这正是 TF32 与 [[learning/precision/fp16|fp16]] 的本质差别：fp16 只有 5 位指数、范围窄到约 $6.5\times10^4$ 就会溢出为 `inf`，而 TF32 不会。

### 关键数值

| 指标 | 数值 |
| --- | --- |
| 有效精度 | **11 bit**（10 位尾数 + 隐式前导 1） |
| 单位舍入 $u$ | $u = 2^{-11} \approx 4.88\times10^{-4}$ |
| 十进制有效位 | $11\log_{10}2 \approx 3.3$ 位 |
| 最小正规数 | $2^{-126} \approx 1.18\times10^{-38}$（同 fp32） |
| 最大量级 | $\approx 3.40\times10^{38}$（量级同 fp32，因只有 10 位尾数，顶端比 fp32 的 $3.4028\times10^{38}$ 略小约 0.05%） |

单位舍入 $u = 2^{-11}\approx4.88\times10^{-4}$ 是"每次运算相对误差的下限"。它比 fp32 的 $2^{-24}\approx5.96\times10^{-8}$ 大了约 4 个数量级——这就是 TF32 的代价：**精度上退到 fp16 的水平，但范围保住了 fp32 的水平**。

### 和相邻格式的对比

| 格式 | 指数位 | 尾数位（含隐式） | 十进制有效位 | 单位舍入 $u$ | 最小正规数 | 最大量级 | 存储位宽 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| bf16 | 8 | 8 | ≈2.4 | $2^{-8}\approx3.9\times10^{-3}$ | $1.18\times10^{-38}$ | $3.40\times10^{38}$ | 16 |
| fp16 | 5 | 11 | ≈3.3 | $2^{-11}\approx4.9\times10^{-4}$ | $6.10\times10^{-5}$ | $6.55\times10^{4}$ | 16 |
| **TF32** | **8** | **11** | **≈3.3** | $2^{-11}\approx4.9\times10^{-4}$ | $1.18\times10^{-38}$ | $3.40\times10^{38}$ | **32（用 19）** |
| fp32 | 8 | 24 | ≈7.2 | $2^{-24}\approx6.0\times10^{-8}$ | $1.18\times10^{-38}$ | $3.40\times10^{38}$ | 32 |

这张表读出来是三条清晰的关系：

1. **TF32 = fp16 的精度 + fp32 的范围。** 尾数位（11）和单位舍入（$2^{-11}$）跟 fp16 一模一样；指数位（8）和范围跟 fp32 一模一样。NVIDIA 官方也直言它"比 bf16 精度更高、与 fp16 精度相同、范围同 fp32"。
2. **TF32 比 bf16 更"准"，但同属一个"宽范围"家族。** bf16 只有 7 位尾数（8 位有效），$u \approx 3.9\times10^{-3}$，比 TF32 的 $4.9\times10^{-4}$ 差约 8 倍；两者范围相同。
3. **TF32 的唯一短板是精度，不是范围。** 和 fp32 相比，它整整少了 13 位有效数字，把一个 $10^{-8}$ 量级的误差放大到了 $10^{-4}$ 量级。

相关阅读：[[learning/precision|精度总览]]、[[learning/precision/fp16|fp16]]、[[learning/precision/bf16|bf16]]、[[learning/precision/fp32|fp32]]。

### 什么时候需要它

TF32 的适用场景，本质是一个**精度-vs-范围-vs-成本**的三方权衡里"中间那条路"被硬件点亮的时刻：

1. **单精度训练/推理需要张量核心加速，且精度余量足够。** 在 Ampere 上，TF32 的张量核心吞吐约为 fp32 CUDA 核心的 8 倍（表格口径：FP32 = 1x，TF32 = 8x，fp16/bf16 = 16x）。实践中从 V100（纯 fp32）迁到 A100（TF32），很多视觉 / NLP 模型端到端能拿到 **2–6x** 加速，且**不用改模型脚本、不用调超参**。

2. **既想要 fp32 的动态范围，又愿意付 fp16 级别的精度。** 如果数据跨度大、用 fp16 会溢出到 `inf`（比如 attention 里的较大 logits、某些优化器状态），TF32 因为保留了 8 位指数而不会溢出，同时丢的精度远小于 fp16 溢出带来的"完全错误"。

3. **作为混合精度训练的"零改动起点"。** TF32 最大的诱惑是**无感**：所有存储仍是 fp32，只有 matmul / conv 内部偷偷用张量核心。它不需要 fp16 的 loss scaling、不需要手动 `half()` cast、不需要 scale 出 NaN 后重试，因此是用 A100 跑旧 fp32 脚本的最低成本提速方案。真要进一步提速，再上原生 16-bit 混合精度（fp16/bf16 的吞吐是 TF32 的 2 倍，还减半内存带宽）。

### 什么时候不用它

1. **需要完整 fp32 精度时。** 科学计算、矩阵求逆 / 各类分解、条件数大（ill-conditioned）的线性系统，这些场景里 TF32 的 $4.9\times10^{-4}$ 单位舍入会被条件数 $\kappa$ 进一步放大，结果可能错得离谱。此时应把 `matmul.allow_tf32 = False`，退回纯 fp32 甚至上 [[learning/precision/fp64|fp64]]。

2. **在意内存和更高吞吐时。** TF32 存储仍是 32 bit（不省内存、不省带宽），且吞吐只有 fp16/bf16 的一半。若数据范围可控、不会溢出，fp16/bf16 混合精度是比 TF32 更优的选择。

3. **在非 NVIDIA 硬件或 CPU 上运行时。** TF32 是 NVIDIA 专属的、只能跑在 Ampere 及之后架构的张量核心上；CPU、AMD、手机 SoC 都不会理解它，代码也没有任何可移植的 TF32 dtype。

4. **算子本身不是 matmul / conv 时。** TF32 只加速"乘加"类算子（线性层、全连接、注意力、卷积）。batchnorm、优化器 step、逐元素算子、以及 fp16/bf16/fp64/int 张量上的操作，都不会走 TF32——别指望它全局提速。

5. **需要严格可复现的逐位结果时。** TF32 的舍入顺序与 kernel 选择在不同配置下可能不同，带来 run-to-run 差异；对训练收敛有确定性要求的调试场景，应关闭 TF32。

### 硬件与软件现状

**硬件——只有 NVIDIA 张量核心，只有"计算模式"。** TF32 由 **Ampere（A100/A30，以及 GA10x 消费级 RTX 30 系）** 引入，之后 **Hopper（H100/H800）、Ada（RTX 40）、Blackwell** 张量核心持续支持。它绝不是一个存储类型：

- 内存和寄存器里**始终是 fp32**（或脚本里指定的格式）；
- 只有卷积和矩阵乘在**乘法发生前那一瞬**把输入转成 TF32；
- 没有 `tf32` 这个 dtype，你无法声明一个 TF32 张量，也无法选择 TF32 作为 tensor 类型。

**软件——框架默认行为（这是最容易踩坑的地方）：**

| 层 / 库 | 默认行为 | 如何切换 |
| --- | --- | --- |
| cuDNN（conv） | **默认用 TF32**（8.0+，`CUDNN_DEFAULT_MATH` / `CUDNN_TENSOR_OP_MATH`） | `cudnn.allow_tf32 = False` 关闭 |
| cuBLAS（matmul） | **默认 FP32**（`CUBLAS_DEFAULT_MATH`），TF32 需显式开启 | `cublasSetMathMode(CUBLAS_TF32_TENSOR_OP_MATH)` 或 `CUBLAS_COMPUTE_32F_FAST_TF32` |
| cuTENSOR | 1.1.0+ 支持，compute type 由 API 指定 | `CUTENSOR_COMPUTE_TF32` |
| PyTorch | `cuda.matmul.allow_tf32`：1.7–1.11 默认 **True**，1.12 起默认 **False**；`cudnn.allow_tf32`：默认 **True** | 见下方代码示例 |
| TensorFlow / NGC | 官方镜像与 TF 2.4+ 在 Ampere 上默认开启 TF32 | 环境变量 `NVIDIA_TF32_OVERRIDE=0` 全局强制关闭 |

一个需要特别留意的细节：**PyTorch 对 matmul 和 conv 的默认值是相反的**。`torch.backends.cuda.matmul.allow_tf32` 自 1.12 起默认 `False`（矩阵乘用纯 fp32），而 `torch.backends.cudnn.allow_tf32` 一直默认 `True`（卷积用 TF32）。所以"在 Ampere 上我的 fp32 卷积被偷偷加速了，但矩阵乘没有"是非常常见的困惑来源。自 PyTorch 2.9 起官方建议改用更细粒度的 `fp32_precision` 接口（旧的 `allow_tf32` 已标记弃用）。

### 代码示例：在 PyTorch 里开关 TF32

下面的脚本用一次大矩阵乘，同时测 TF32 开 / 关的时间和相对误差（以 fp64 结果为参考），直观展示"7 倍速度、2 个数量级误差"的权衡：

```python
import torch

assert torch.cuda.is_available()
print("GPU:", torch.cuda.get_device_name(0),
      "| compute capability:", torch.cuda.get_device_capability(0))

a = torch.randn(4096, 4096, device="cuda")
b = torch.randn(4096, 4096, device="cuda")
a64, b64 = a.double(), b.double()
ref = a64 @ b64                    # fp64 参考
mean = ref.abs().mean()

def bench(use_tf32):
    # 控制矩阵乘是否允许 TF32（PyTorch 1.12+ matmul 默认 False）
    torch.backends.cuda.matmul.allow_tf32 = use_tf32
    torch.backends.cudnn.allow_tf32 = use_tf32
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()
    out = a @ b
    end.record()
    torch.cuda.synchronize()
    rel = (out.double() - ref).abs().max().item() / mean.item()
    return start.elapsed_time(end), rel

t_tf, e_tf = bench(True)
t_fp, e_fp = bench(False)
print(f"TF32 : {t_tf:7.1f} ms  相对误差 = {e_tf:.2e}")
print(f"FP32 : {t_fp:7.1f} ms  相对误差 = {e_fp:.2e}")
print(f"速度提升 = {t_fp / t_tf:.1f}x（TF32 相对 FP32）")

# PyTorch 2.9+ 推荐的新接口（旧 allow_tf32 已弃用）
torch.backends.cuda.matmul.fp32_precision = "ieee"   # 或 "tf32"
torch.backends.cudnn.conv.fp32_precision = "tf32"

# 更粗粒度的全局开关：让所有 fp32 matmul 都用库默认精度
# torch.set_float32_matmul_precision("highest" | "high" | "medium")
```

运行要点：

- 矩阵要够大（如 $4096^2$ 以上），cuBLAS 才会真正挑中 TF32 kernel；太小则速度体现不出来。
- `torch.backends.cuda.matmul.allow_tf32` 只影响 matmul，`torch.backends.cudnn.allow_tf32` 只影响卷积，两者独立，别只设一个。
- Linux 下全局强制关闭：启动前设 `NVIDIA_TF32_OVERRIDE=0`，可一次性压制库和框架的所有 TF32 设置，用于排查结果是不是 TF32 导致的。

### 一些 tips

1. **先确认硬件，再谈开关。** TF32 只在 Ampere 及之后的 NVIDIA 张量核心上生效。旧卡（Volta/Turing）上没有这个模式，设了 `allow_tf32` 也毫无效果——这是很多老代码"怎么设都没用"的原因。

2. **matmul 和 conv 是两把独立的锁。** PyTorch 里 `cuda.matmul.allow_tf32`（默认 False）和 `cudnn.allow_tf32`（默认 True）互不影响。要完全复现 fp32 数值，两把都要关。

3. **别拿 TF32 当存储格式。** 没有 `tf32` dtype，也不会有 `torch.tf32` 张量。想省内存、想真正以半精度存储，请用 fp16/bf16。

4. **精度富余才划算。** 只要你的任务对 $10^{-4}$ 量级的相对误差不敏感（绝大多数深学习训练/推理都如此），TF32 就是白送的提速。一旦训练出现不收敛、loss 抖动、或在敏感层（如 attention 的 softmax 前）精度掉得离谱，优先关掉 TF32 定位问题。

5. **想要"极致的范围+极高的吞吐"，不要指望 TF32。** TF32 的范围和 fp32 相同，但吞吐只有 fp16/bf16 的一半。真正的极限速度在原生 16-bit 混合精度（配合 loss scaling），TF32 只是那个"不用改代码就拿到 8 倍"的中间站。
