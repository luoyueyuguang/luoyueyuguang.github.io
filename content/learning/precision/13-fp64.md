聊浮点精度，fp16 / bf16 / fp8 天天在 AI 里见，但一提到"科学计算的主力"、"double"、"精确的参考真值"，说的是同一个东西：**fp64（IEEE 754 binary64，双精度）**。它是绝大多数程序设计语言里默认的浮点类型（C printf 的 `%f`、Python 的 `float`、NumPy 的默认 dtype 都是它），也是理解其它一切精度格式的锚点。

> fp64 是"标准答案"：53 位有效数字（约 16 位十进制）、单位舍入约 $10^{-16}$，既够算绝大多数物理/工程问题，又足够便宜（CPU 上几乎全速、原生硬件）。它的问题在于**比 fp32 慢、且不解决病态问题**。AI 里大多数场景连它一半的精度都用不上。

### 位布局

binary64 是 IEEE 754 里最"标准"的格式之一，浮点运算的"默认档"：

| 字段 | 位数 |
| --- | --- |
| sign | 1 |
| exponent | 11（偏置 1023） |
| fraction | 52 |
| 总计 | 64 |

普通数（规约数，normal）的表示：

$$
x = (-1)^s \cdot 2^{E - 1023} \cdot (1.f)_2
$$

其中 $s$ 是符号位，$E$ 是 11 位指数（取值 $1 \ldots 2046$），$f$ 是 52 位尾数。隐式前导 1 加上 52 位存储尾数，得到 **53 位有效精度**。

- $E = 0$ 时表示 0 或**次规约数**（subnormal），此时没有隐式前导 1：$x = (-1)^s \cdot 2^{-1022} \cdot (0.f)_2$，用来填充 0 附近更小的数。
- $E = 2047$ 时表示 $\pm\infty$ 或 NaN。

**指数偏置 1023**，所以真实指数范围是 $E - 1023 \in [-1022, 1023]$。fp64 的有效数字只有 53 位，但指数范围非常大。它把精度和范围都做到"够用"，这正是它作为默认格式的原因。

### 关键数值

| 指标 | 值 | 说明 |
| --- | --- | --- |
| 有效精度 | 53 bit | 52 位尾数 + 隐式前导 1 |
| 单位舍入 $u$ | $2^{-53}$ | $\approx 1.11 \times 10^{-16}$ |
| 十进制有效位 | $53 \log_{10} 2$ | $\approx 15.95 \approx 15.9$ 位 |
| 最大有限值 | $(2 - 2^{-52}) \cdot 2^{1023}$ | $\approx 1.80 \times 10^{308}$ |
| 最小规约数 | $2^{-1022}$ | $\approx 2.23 \times 10^{-308}$ |
| 最小次规约数 | $2^{-1074}$ | $\approx 4.94 \times 10^{-324}$ |
| $\varepsilon_{\text{mach}}$ | $2^{-52}$ | $\approx 2.22 \times 10^{-16}$（相邻可表示数间距） |

单位舍入 $u = 2^{-53}$ 决定"相对误差的下限"：每次四舍五入最多引入约 $u$ 的相对误差。它是判断"double 够不够"的核心量。够不够，取决于你问题的**条件数 $\kappa$** 与 $u$ 的乘积 $\kappa u$ 是否越过容忍线。

### 和相邻格式的对比

| 格式 | 指数位 | 尾数位（含隐式） | 十进制有效位 | 单位舍入 | 最大量级 |
| --- | --- | --- | --- | --- | --- |
| fp16 | 5 | 11 | ≈3.3 | $2^{-11}$ | $10^5$ |
| fp32 | 8 | 24 | ≈7.2 | $2^{-24}$ | $10^{38}$ |
| **fp64** | **11** | **53** | **≈15.9** | $2^{-53}$ | $10^{308}$ |
| fp128 | 15 | 113 | ≈34.0 | $2^{-113}$ | $10^{4932}$ |

fp64 的单位舍入 $2^{-53} \approx 1.1 \times 10^{-16}$，对比 fp32 的 $2^{-24} \approx 6.0 \times 10^{-8}$，**两者差 8 个数量级**。当问题把误差放大 $10^8$ 倍时，fp32 的结果已经全错，而 fp64 只损失最后一位有效数字。

选择相邻格式的直觉：

- **上起**：fp64 不够时，`[[learning/precision/15-fp128|fp128 四精度]]`（或 double-double）是下一步；fp64 是切换到高精度前的"最后一档普通精度"。
- **下落到 AI 一侧**：`[[learning/precision/12-fp32|fp32]]` 是默认单精度，`[[learning/precision/10-bf16|bf16]]` 用 8 位指数以精度换范围，`[[learning/precision/09-fp16|fp16]]` 是受限范围的单精度。回到 [[learning/precision/01-overview|精度总览]] 能看到全貌。

### 什么时候需要它

判据和任何精度格式一样：**误差被放大到多少**。相对误差的增长由条件数 $\kappa$ 控制。输入相对误差 $u$ 经过问题放大，输出相对误差约 $\kappa u$。

- 若 $\kappa u_{32} \approx 10^{-6}$，fp32 已经给出 6 位精确结果，够用，不必上 fp64。
- 但若 $\kappa \sim 10^{10}$（病态系统、近奇异矩阵、长时间积分），fp32 的 $\kappa u_{32} \sim 10^2$ 直接崩掉；fp64 的 $\kappa u_{64} \sim 10^{-6}$ 依然可用。

所以 fp64 必需的是这些场景：

1. **病态线性系统**。Hilbert 矩阵 $H_{ij} = 1/(i+j-1)$ 条件数随阶数指数上升，$n=8$ 时 $\kappa \approx 10^{10}$，fp32 已经救不回来；这是"残差小、解却错得离谱"的经典来源。数值线性代数、有限元、结构力学的求解器默认就用 double。

2. **参考真值 / 验算基准**。想验证 fp32/bf16/fp8 的误差、做 quantization 误差分析、或确认某个算法的正确性，需要一个"足够精确"的参考。fp64 是这条链上的最低标准，比它更精确的 fp128 通常只用来当更严格的参考。

3. **长期数值积分 / 物理演化**。轨道力学、分子动力学、数值微分方程，误差随步数累积（$\sim \sqrt{N} u$ 或更糟）。fp32 在 $10^5$ 步后就显出偏差，fp64 能把可靠积分推到 $10^8 \sim 10^{10}$ 步；缺了它，长时间尺度上的结果没有意义。

4. **中间需要大范围**。注意有些任务"精度够、范围不够"：bf16 的指数只有 8 位（最大量级 $10^{38}$，实际尾数更小），fp16 最大才 $10^5$。当你需要在 $10^{-100}$ 到 $10^{100}$ 之间做运算又不想用归一化技巧时，fp64 的指数范围（±$10^{308}$）是它相对所有低精度格式的独特优势：**fp64 既是精度的兜底，也是范围的兜底**。

### 什么时候不用它（AI 语境）

在 AI 里 fp64 通常被避免，原因是**贵，且大多数时候用不上**。

- **吞吐量差距**。GPU 上 fp64 的吞吐通常是 fp32 的 **1/2（数据中心卡，如 A100/H100 的 CUDA core）到 1/32 甚至 1/64（消费级 GeForce 的 fp64 单元被大幅裁剪）**。而且 **tensor core 压根不做 fp64**，它只做 TF32/FP16/BF16/FP8/INT8。所以想在 GPU 上拿 fp64 做矩阵乘，要么用 CUDA core 硬算（慢一个数量级），要么根本无从加速。反观 CPU，fp64 是原生全速的。

- **AI 用不上那么高精度**。神经网络训练/推理对精度的需求通常在 fp32 附近甚至更低：梯度噪声、dropout、batch 里的随机性使得"模拟真值"的精度并不需要 16 位十进制。训练大多用 fp32/bf16/fp16/fp8，fp64 只在寥寥几种情况出现：**master weights（主权重，偶尔用 fp32 而非 fp64）**、极少数需要数值稳定的算子、以及硬件/框架的精度基准测试。

- **fp64 不解决病态**。上面那个 $[10^{16}, 1, -10^{16}]$ 的抵消例子，fp64 一样会算成 0。**它不修复条件数，只缩小舍入常数**。病态问题需要改算法（重排求和、补偿求和、Kahan）或求助于 `[[learning/precision/16-ozaki-scheme|Ozaki 整数精确点积]]` / double-double。

**fp32/bf16 对付不了的问题，先别急着上 fp64：先量化 $\kappa$，再决定是升精度还是改算法。** 只有当你确认"误差确实来自舍入、且 $\kappa u_{64}$ 在容忍线内"时，fp64 才是正解。

### 硬件和软件现状

fp64 是少数"CPU 全速、GPU 半速、TPU 没有"的格式，这一点和它作为科学计算主力的身份形成有趣反差。

- **CPU（x86-64 / AArch64）**：原生硬件支持，几乎全速。C 的 `double`、Fortran 默认 real、NumPy 默认 dtype `float64` 都是它。SSE2 / AVX-/AVX-512 的 `addpd`/`mulpd` 直接做双精度向量运算。**注意**：x86 的 `long double` 是 **80 位扩展精度（fp80）**，二者位布局完全不同。

- **GPU / CUDA**：`double` 类型存在、C++ 里 `__device__` 也能直接用，但吞吐按前文所述骤降。数据中心卡约 1/2，消费级约 1/32~1/64。做矩阵乘要用 CUDA core（或 cuBLAS 的 fp64 路径），**无法用 tensor core**。需要更高精度时，GPU 上通常手写 double-double（用两个 double 拼约 106 位），这比 fp64 还慢，但至少能跑。

- **TPU**：**没有 fp64 支持**。TPU 的计算单元基于 bfloat16/fp32/int，TensorFlow/JAX 里显式要求 fp64 的算子会被拒绝或落到 host CPU。想在 TPU 上跑科学计算要么用 fp32，要么完全放弃。

- **框架**：NumPy 默认 `float64`；PyTorch 的 `torch.float64`（`tensor.double()`）；TensorFlow `float64`（GPU 上慢，TPU 不支持）；JAX 默认 **fp32**，要开 `jax.config.update("jax_enable_x64", True)` 才解除。**默认行为差异是个常见坑**：JAX/Rust 一些库默认 32 位，C/Python 默认 64 位，跨语言搬运数据时 dtype 可能悄悄降级。

- **存储格式 vs 计算格式**：fp64 是一个存储格式：数据可以按 64 位存盘（`.npy`、HDF5、pickle），代价是内存/带宽是 fp32 的两倍。这与 TF32/FP8 不同：它们是**纯计算格式**（存储仍然用 fp32/fp16，只在计算时降低精度）。所以"用 fp64"要分清两层：**存 fp64 很便宜（只是两倍内存），算 fp64 才贵（CPU 全速、GPU 慢）**。

### 代码示例

用 NumPy 演示 fp64 相比 fp32 在**累加误差**上的差别，以及 fp64 **同样救不了抵消**：

```python
import numpy as np

def total(v, dtype, n):
    """按给定精度累加 v 共 n 次。"""
    s = dtype(0.0)
    for _ in range(n):
        s += dtype(v)
    return s

n = 1_000_000

# 1) 累加 0.1：0.1 在二进制里不是精确值，舍入误差逐次累积
print(f"sum 0.1 x {n}:")
print(f"  float64 = {total(0.1, np.float64, n):.15f}   # 精确 {n * 0.1}")
print(f"  float32 = {total(0.1, np.float32, n):.9f}    # 差 ~1e3")

# 2) 灾难性抵消：1.0 在两种精度里都被抹掉
print(np.sum(np.array([1e16, 1.0, -1e16], dtype=np.float64)))  # -> 0.0，应为 1.0
print(np.sum(np.array([1e16, 1.0, -1e16], dtype=np.float32)))  # -> 0.0
```

运行结果（本机实测）：

```
sum 0.1 x 1000000:
  float64 = 100000.000001332882675   # 精确 100000.0
  float32 = 100958.343750000         # 差 ~1e3
0.0
0.0
```

读法：

- **累加误差**：`0.1` 本身不是精确二进制值（存成 `0.1000000000000000055...`），单个误差极小，但重复 $10^6$ 次后，fp32 的误差被放大到约 $10^3$（每加一次都在吞掉低位），fp64 只差 $1.3 \times 10^{-6}$。这说明了 fp64 把舍入误差压到几乎不可见。
- **抵消**：`1e16 + 1.0` 时，`1.0` 小于 `1e16` 的 ulp（约 2.0），被直接舍掉；最后 `1e16 - 1e16 = 0`。**fp64 一样算错**：它只缩小舍入常数，不修复病态。这类问题要靠改算法（重排、补偿求和）或 `[[learning/precision/16-ozaki-scheme|Ozaki 整数精确点积]]` / double-double。

如果想看 fp64 相对 fp32 在**累加十万项**时的相对误差，用补偿求和（Kahan）作参考：

```python
def kahan_sum(a):
    s = c = np.float64(0.0)
    for x in a:
        y = x - c
        t = s + y
        c = (t - s) - y
        s = t
    return s

N = 1_000_000
ref = kahan_sum(np.array([1.0 / i for i in range(1, N + 1)], dtype=np.float64))
for dt in (np.float64, np.float32):
    s = dt(0.0)
    for i in range(1, N + 1):
        s += dt(1.0) / dt(i)
    print(f"{dt}: 相对误差 = {abs(float(s) - ref) / ref:.2e}")
```

实测：`float64: 5.1e-14`，`float32: 2.5e-03`。两个精度相差 11 个数量级，说明用 double 累加，误差近乎消失。

### 一些 tips

1. **先量化，再升级**。算一下 $\kappa$ 或误差增长速度：若 $\kappa u_{32}$ 已经小于容忍线，fp32 就够了，fp64 只是把内存翻倍、把 GPU 速度砍半。需要的情况都出现在 $\kappa u$ 越过红线的地方。
2. **fp64 不治抵消，治"丢失的低位"**。`[1e16,1,-1e16]` 这类抵消在 fp64 下同样归零。遇到它，先换算法（从大往小加、Kahan、`math.fsum`/`np.longdouble` 向量化），再谈升精度。
3. **跨语言注意默认 dtype**。C/Python/NumPy 默认 64 位；JAX 默认 32 位（要 `jax_enable_x64`）；PyTorch 新建张量默认 32 位（`.double()` 才转 64）。数据搬运时 dtype 悄悄降级是无声的坑。
4. **别把 `long double` 当 fp64 或 fp128**。x86 上是 **80 位扩展精度（fp80）**，AArch64 上可能真 binary128，PPC64LE 上是 **double-double**。三平台三种语义，跨平台代码别依赖它。
5. **fp64 兜底范围，不只是精度**。当你需要在 $\pm10^{300}$ 的跨度上做运算又不想手动归一化，fp64 的指数范围是它相对 fp16/bf16/fp32 的关键优势；而**更高精度**的需求才轮到 `[[learning/precision/15-fp128|fp128]]` 或 double-double。
