聊精度，fp64（double）几乎统治一切；但在 x86 上认真写数值代码，你会撞见一个很特别的格式：**fp80（x87 extended precision，binary80）**。它是 Intel 在 1980 年代为 x87 浮点协处理器定义的一种"增强版 double"，不在 IEEE 754 标准之内：**64 位有效数字**（比 double 的 53 位多 11 位，约合 19 位十进制），指数范围却跟 fp128 一样宽，却只占 10 字节。它快、它准，可它处处是坑。

> fp80 是 x86 平台的"高精度中间态"：它把 double 的 53 位有效数字拉到 64 位，同时把指数范围拉到和 fp128 一个量级，而且只在 x87 上有原生硬件。它更像是"顺手就能拿到的免费高精度"，不算被标准认可、跨平台一致的正式格式，所以它很便宜，但不可移植、行为怪异。

### 位布局

binary80 是 **Intel 私有格式，不在 IEEE 754 标准之内**。它和其它 IEEE 格式最大的不同是：**整数位是显式存储的**（explicit integer bit，也叫显式前导 1 / j-bit），而不是像 fp64 / fp128 那样隐式略去。

| 字段 | 位数 |
| --- | --- |
| sign | 1 |
| exponent | 15（偏置 16383） |
| significand | 64（**包含显式的整数位**） |
| 总计（数据位） | 80 |

值公式和 fp64 / fp128 形式上同构，但 `1.` 不是"隐式前导 1"，而是**实实在在地存进 64 位 significand 的最高位**：

$$
x = (-1)^s \cdot 2^{E - 16383} \cdot (1.f)_2
$$

其中 significand 那一整块（整数位 `1` + 63 位小数部分 `f`）就是 64 位，所以有效精度正好 **64 bit**。指数偏置 *bias = 16383*（和 fp128 相同）。

```
+--------+-----------------+--------------------------------------+
| sign 1 | exponent 15     | significand 64  (含显式整数位 1 + 63 位 f)|
+--------+-----------------+--------------------------------------+
  第79位                   第78...64位                     第63...0位
```

因为这个整数位是显式的、可以取 0，x87 才允许"unnormal"（整数位为 0 但指数位合法）这类非标准表示，这是它"不符合标准"的直接来源。存储时数据占 **10 字节**（80 位），为对齐在 C 里通常补到 **16 字节**（`sizeof(long double)` 在 x86-64 上实测为 16）。

### 关键数值

| 指标 | 值 |
| --- | --- |
| 有效精度 | 64 bit |
| 单位舍入 / 机器精度 | $u = 2^{-63} \approx 1.08 \times 10^{-19}$ |
| 十进制有效位 | $\approx 64\log_{10}2 \approx 19.3$ |
| 最小正规数 | $2^{-16382} \approx 3.36 \times 10^{-4932}$ |
| 最大 | $\approx 2^{16384} \approx 1.19 \times 10^{4932}$ |

要点：fp80 的机器精度 $2^{-63} \approx 1.08 \times 10^{-19}$，比 double 的 $2^{-53} \approx 1.11 \times 10^{-16}$ 小约 **3 个数量级**；指数范围则和 fp128 一个级别（±10⁴⁹³²）。也就是说，fp80 是"double 精度不够、但又不值得上软件模拟 fp128"时的甜点。

把几个相邻格式放在一起（注意 fp80 的尾数位数是"含显式前导 1"的 64 位，其它格式的尾数位数是"含隐式前导 1"）：

| 格式 | 指数位 | 尾数位（含前导） | 十进制有效位 | 单位舍入 | 最大量级 | 硬件 |
| --- | --- | --- | --- | --- | --- | --- |
| fp32 | 8 | 24 | ≈7.2 | $2^{-24}$ | $10^{38}$ | 原生 |
| [[learning/precision/13-fp64\|fp64]] | 11 | 53 | ≈15.9 | $2^{-53}$ | $10^{308}$ | 原生（SSE2） |
| **fp80** | **15** | **64** | **≈19.3** | $2^{-63}$ | $10^{4932}$ | **仅 x86/x87** |
| [[learning/precision/15-fp128\|fp128]] | 15 | 113 | ≈34 | $2^{-113}$ | $10^{4932}$ | 无 / 软件 |

### 什么时候需要 fp80

fp80 的价值在于"**免费的高精度**"：你在 x86 上只要用 `long double`，就能比 double 多拿约 3 位十进制精度，而且不需要任何第三方库。

1. **double 精度差一点的病态问题**。当你的条件数 $\kappa$ 落在 $10^{16}$ 到 $10^{19}$ 之间时，double 的输出相对误差 $\kappa u_{64}$ 已经越过容忍线；换 fp80 后 $\kappa u_{80}$ 能救回来，而又不必付出 fp128 软件模拟的数量级代价。

2. **迭代精化（iterative refinement）的残差计算**。解 $Ax=b$ 时用 double 做分解，再用更高精度算残差 $r = b - A\hat{x}$。在 x86 上 `long double` 是天然的"高精度残差载体"，比手写 double-double 省心。

3. **长序列累加 / 求和**。$N$ 项求和的最坏误差 $\sim N u$。fp80 把 $u$ 从 $2^{-53}$ 压到 $2^{-63}$，在 $N$ 很大时把累积误差再往下推 3 个量级。

4. **求高精度常量 / 测量低精度格式的误差**。想拿一个"比 double 更准的参考"去测 fp16 / fp8 / 自定义格式的舍入误差，fp80 的 $2^{-63}$ 足以当作近真值参考。

### 什么时候不用 fp80

1. **要跨平台可移植**。`long double` 在 x86-64（GCC/Clang）上是 80-bit 扩展，在 AArch64 上是真正的 binary128，在 PPC64LE 上是 double-double，在 MSVC（Windows x64）上干脆就是 double。同一个"高精度类型"，四种平台四种语义。跨平台数值代码如果指望 `long double` 一致，会翻车。更多可参考 [[learning/precision/15-fp128|fp128]]。

2. **要严格符合 IEEE 754**。fp80 不是标准格式：显式整数位、unnormal 数、以及 x87 特有的 excess precision 行为，都让它在不同编译器 / 优化级别下可能给出不同结果。需要精确、可复现的舍入语义时，用标准宽度（fp64 / fp128）更稳。

3. **需要超过 19 位十进制**。fp80 只在 double 基础上前进约 3 位十进制；需要 32~34 位时，用 [[learning/precision/15-fp128|fp128]] 或 double-double。

4. **在 GPU 上**。CUDA / 绝大多数 GPU 根本没有 fp80：`long double` 在 nvcc 里就是 double 的别名，硬件只提供 fp16 / bf16 / fp32 / fp64。

### 硬件与软件现状

**核心事实：fp80 只在 x86 上存在，而且是"既能存又能算"的原生格式。**

- **唯一原生硬件：x86 / x87**。Intel 与 AMD 的 x87 浮点单元是唯一直接实现 80-bit 扩展精度算术的硬件。x86-64 上 `long double` 的运算仍然走 x87 指令；而普通 `double` 在 x86-64 默认改用 **SSE2**（严格一次舍入、完全符合 IEEE）。
- **存储格式 vs 计算格式**：fp80 **同时是存储格式和原生计算格式**，这跟只作计算中间态的格式（比如只在寄存器里用、存回低精度的 [[learning/precision/11-tf32|tf32]]）不同。它既是 `long double` 的存储形态（10 字节），又有配套的寄存器指令。
- **软件 / 编译器**：GCC、Clang 在 x86-64 与 32 位 i386 上把 `long double` 映射为 80-bit 扩展（`LDBL_MANT_DIG == 64`）。其它平台语义各异，见上。
- **历史包袱**：1990 年代 x87 是唯一的标量浮点单元，它把所有 `double` 运算都放进 80-bit 寄存器做，于是出现著名的 **excess precision / double rounding**。

#### excess precision：为什么 1990 年代会有"结果不一致"

x87 的做法是：double 操作数先被**扩展进 80-bit 寄存器**，运算在 80-bit 里进行，最后存储回 double 时才**再舍入一次**。这等于"本应在 53 位处舍入的操作，先在第 64 位舍入、再在 53 位舍入"，级联两次舍入（double rounding）有时和"一次正确舍入"得到不同的位。于是同一段 `double` 代码在 x87 上、与在"严格一次舍入"的机器上（或后来的 SSE2 x86-64）可能给出**不同的结果**。

这曾是 C 标准语义争论的焦点，也是数值库在 1990s 频繁踩坑的根源（编译器用 `-fexcess-precision=standard` 之类的开关来收紧）。SSE2 普及后，x86-64 默认对 `double` 用 SSE2，彻底绕开了 x87 的 excess precision；x87 只留给 `long double`，代价是 `long double` 在现代 x86-64 上不是 SIMD 路径，速度明显慢于 `double`。

### 代码示例

x86-64 上用 GCC/Clang 编译：`long double` 就是 80-bit 扩展，能保存一个 `double` 存不了的小量。下面的例子在 `1.0 + 1e-19` 上对比两种类型：`1e-19` 小于 double 在 `1.0` 处的半 ulp（$2^{-53}$），所以被 `double` 舍掉；但 `1e-19` 落在 80-bit 的 64 位有效数字之内，被 `long double` 完整保留。

```c
#include <stdio.h>
#include <float.h>

int main(void) {
    /* 在 x86-64 + GCC/Clang 上，long double 就是 80-bit x87 扩展精度 */
    printf("LDBL_MANT_DIG = %d, DBL_MANT_DIG = %d\n",
           LDBL_MANT_DIG, DBL_MANT_DIG);        /* 64 vs 53 */
    printf("sizeof(long double) = %zu\n", sizeof(long double)); /* 16 */
    printf("LDBL_EPSILON = %Le\n", LDBL_EPSILON);   /* ~1.08e-19 */

    long double x = 1.0L + 1e-19L;   /* 1e-19 < double 在 1.0 处的半 ulp */
    printf("1 + 1e-19 (long double) = %.21Lg\n", x);      /* 保留下来 */
    printf("1 + 1e-19 (double)      = %.17g\n", 1.0 + 1e-19); /* 舍回 1.0 */
    return 0;
}
```

在 x86-64 Linux（GCC）上的实际输出：

```text
LDBL_MANT_DIG = 64, DBL_MANT_DIG = 53
sizeof(long double) = 16
LDBL_EPSILON = 1.084202e-19
1 + 1e-19 (long double) = 1.00000000000000000011
1 + 1e-19 (double)      = 1
```

`1.0 + 1e-19` 在 `double` 里退化回 `1.0`，在 `long double` 里被完整保留到第 19 位。这就是 fp80 那"多余的 11 位"起作用的样子。把这段代码拿到 AArch64 上，`long double` 会变成真正的 binary128（软件模拟，输出更长的精度但语义不同）；拿到 MSVC 上则是 `double`。**同一个源文件，三种结果。**

### 一些 tips

1. **`long double` 不是 portable 的高精度类型**。x86-64（GCC/Clang）= 80-bit；AArch64 = binary128；PPC64LE = double-double；MSVC（Windows x64）= 就是 `double`。跨平台数值代码别拿它当"高精度 double"，否则各平台结果不一致。参见 [[learning/precision/15-fp128|fp128]] 里的移植警告。

2. **打印用 `%Lg` / `%Le`**（C 的 `L` 修饰符），不要用 `%f` / `%g` 直接打 `long double`，后者默认按 `double` 转换，精度会丢失。

3. **`2.675` 那类坑和 x87 无关**。`2.675` 在二进制里存成 `2.674999...`，所以 `round(2.675, 2)` 得 `2.67`、`(int)(2.675*100)` 得 `267`。这是十进制表示 / 截断问题，不是 x87 excess precision；两者常被混在一起提。要精确十进制，用整数 scaling 或十进制浮点。

4. **别指望 `long double` 永远走 x87**。现代 x86-64 默认对 `double` 用 SSE2（严格舍入），`long double` 才走 x87。两者在性能与舍入语义上都不同，混用时要清楚自己在用哪条路径。

5. **先量化再升级**。fp80 只比 double 好约 3 个数量级，不是数量级性的质变。先算条件数 / 误差增长，确认 double 的 $u \approx 1.1 \times 10^{-16}$ 真不够，再决定是上 fp80、[[learning/precision/13-fp64|fp64]] 配迭代精化，还是直接上 [[learning/precision/15-fp128|fp128]] / double-double。
